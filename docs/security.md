# Защита от случайной публикации секретов

Защита использует бесплатный Gitleaks **8.30.1** со стандартными правилами. Версия и SHA-256 официальных Windows/Linux x64 архивов закреплены в `scripts/install_gitleaks.py`; при обновлении меняют версию и оба хэша вместе. Конфигурации исключений и baseline нет. Значения находок, исходные строки и сообщения коммитов не выводятся: показываются только файл, строка, правило и идентификатор коммита. Временный JSON-отчёт создаётся с полной редактировкой значений и удаляется; в Actions его не загружают.

## Локальная проверка разработчика

Просмотр, preview и использование курса не требуют Gitleaks или hooks. Для разработки из корня репозитория:

```powershell
python scripts/install_gitleaks.py
python -m pip install pre-commit
python -m pre_commit install
```

Установщик поддерживает Windows и Linux x64. На другой платформе установите [официальный бинарный релиз](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1) с проверкой контрольной суммы и добавьте `gitleaks` в `PATH`; скрипт требует ту же версию. Hooks устанавливаются отдельно в каждом клоне. Если уже используются другие Git hooks или `core.hooksPath`, сначала согласуйте их интеграцию; скрипты ручной проверки работают независимо.

Hook проверяет **полное содержимое новых и изменённых файлов в индексе Git**, включая частично staged-файлы, а не только новые строки или рабочую копию. Бинарник должен быть установлен до первого коммита. Отсутствие инструмента или ошибка чтения блокируют проверку. Hooks можно обойти, поэтому они дополняют серверную защиту.

Ручные команды:

```powershell
# История всех доступных refs + рабочие исходники
python scripts/scan_secrets.py source
# Только индекс перед коммитом
python scripts/scan_secrets.py staged
# Полный сайт после сборки
python scripts/check.py
python scripts/scan_secrets.py site
```

История проверяется целиком, без диапазона последних коммитов. В shallow-клоне проверка завершается ошибкой: сначала выполните `git fetch --unshallow --tags`. Для аудита удалённых веток обновите refs через `git fetch origin --prune --tags`; локальная проверка видит только имеющиеся refs, не удалённые сервером или недоступные ветки.

Рабочие исходники — все tracked-файлы (даже игнорируемые сейчас) и новые файлы, которые Git не игнорирует. Удалённые локально файлы покрываются историей. Игнорируемые локальные данные, `design/`, кэши и инструменты не являются исходниками для отправки; **если файл tracked, `.gitignore` его не исключает из проверки**. Сайт сканируется целиком независимо от `.gitignore`, расширения или расположения файла; включено раскрытие поддерживаемых архивов и кодировок до глубины 5. Отсутствующий или пустой сайт считается ошибкой. Symlinks и submodules в исходниках, symlinks в сайте требуют отдельного решения и блокируют соответствующую проверку.

`.gitignore` дополнительно защищает `.env` и локальные варианты, типичные приватные ключи и файлы учётных данных. Безопасные `.env.*.example` допускаются и сканируются; сам проект таких файлов не требует. Для иных локальных конфигураций с паролями используйте `*.secrets.json` или `*.secrets.toml`; временные чувствительные данные держите вне репозитория. Игнорирование файла не делает его безопасным для публикации и не удаляет его из истории.

## CI и публикация

Единственный workflow публикации — `.github/workflows/check.yml`, запускаемый на push, PR и вручную:

1. `source-scan`: checkout с `fetch-depth: 0`, установка проверенного Gitleaks, история всех refs и рабочие исходники.
2. `render` зависит от `source-scan`: тесты, `python scripts/check.py`, затем Gitleaks для **того же `course/_site/`**, который отправляется Pages.
3. Только после успешного сканирования сайта загружается Pages artifact; при PR загрузки нет.
4. `deploy` зависит от обеих jobs и публикует только `main` при push или ручном запуске. Ошибка сканирования, установки, тестов или сборки блокирует загрузку и deployment. Ручной запуск проходит ту же цепочку.

Workflow по умолчанию имеет `permissions: {}`. Checkout/scanning/build получают только `contents: read` и не сохраняют credentials Git. Лишь job `deploy`, без checkout и выполнения кода курса, получает `pages: write` и `id-token: write`. Actions закреплены по полным SHA. Quarto скачивается из публичного релиза без передачи токена; пользовательские secrets в тесты, сборку и Gitleaks не передаются. Используется `pull_request`, поэтому код PR из forks не запускается в контексте `pull_request_target` с повышенными правами.

Тесты защиты: `python -m pytest tests/test_secret_protection.py -q` после установки Gitleaks. Они используют только заведомо фиктивный токен, создаваемый в памяти, и временные репозитории. Без локального бинарника интеграционные тесты пропускаются; в CI установка обязательна и идёт до тестов.

## Если обнаружен секрет

При настоящей утечке **немедленно отзовите или ротируйте секрет у провайдера**, затем исправьте источник и повторите проверки. Не копируйте значение в issue, PR, чат или логи. Удаление строки из последнего коммита не удаляет её из предыдущих коммитов: история проверяется отдельно и продолжит блокировать публикацию. Для удаления из истории согласуйте переписывание истории с владельцем и участниками; форки, клоны и старые артефакты могут сохранять копии. См. [рекомендации GitHub по удалению чувствительных данных](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

Ложное срабатывание разбирайте по файлу, строке и правилу. Предпочтительны исправление примера или безопасная генерация фиктивных данных в тесте. Не вводите blanket-исключения, не отключайте job и не создавайте baseline автоматически. Скрипт явно использует стандартные правила и пустой ignore-файл, игнорирует `gitleaks:allow` и не принимает локальную `.gitleaks.toml` или переменные конфигурации как исключения; точечное исключение требует отдельного проверяемого изменения механизма и объяснения причины.

## Настройки GitHub

Для публичных репозиториев [Secret Scanning](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/detect-secret-leaks/enable-secret-scanning) и [Push Protection](https://github.blog/changelog/2023-05-09-secret-scannings-push-protection-is-available-on-public-repositories-for-free/) доступны бесплатно. Владельцу следует проверить **Settings → Code security** (в некоторых интерфейсах **Code security and analysis**) → **Secret scanning** и **Push protection** → **Enable**. Смотрите предупреждения в **Security → Secret scanning**. Push Protection блокирует поддерживаемые секреты до попадания в GitHub; CI работает уже после отправки и не заменяет эту функцию. Дополнительно проверьте личную настройку **Settings → Code security → Push protection for yourself**.

Проверка API 9 октября 2026 года показала для `temaSW/intro-to-networking`:

- Репозиторий публичный; Secret Scanning и Push Protection уже **enabled** — включать заново не нужно.
- **Settings → Pages → Build and deployment → Source: GitHub Actions** уже используется (`build_type: workflow`). Не переключайте публикацию на ветку.
- Environment `github-pages` допускает только ветку `main`.
- Ветка `main` **не защищена**, rulesets отсутствуют. Владелец должен включить branch protection/ruleset для `main`, требовать PR и обязательные проверки `source-scan` и `render` workflow **Check site**, актуальность ветки перед merge, ограничить обход правил и прямые push. Выберите фактические названия checks после первого запуска обновлённого workflow. Review изменений `.github/workflows/` и скриптов защиты также важен.

Настройки в рамках этой задачи **не изменялись**. Текущий workflow блокирует свою публикацию при ошибках, но без защиты ветки администратор или пользователь с правом записи может изменить/удалить сам workflow либо добавить другой путь deployment. Поэтому гарантировать защиту от обхода на уровне всего репозитория до настройки правил нельзя. Администратор всё равно может менять настройки; GitHub Push Protection допускает документированные обходы и покрывает только поддерживаемые паттерны.

## Границы защиты

Gitleaks ищет известные паттерны и эвристики, а не любые конфиденциальные данные. Бинарные форматы, неподдерживаемые/зашифрованные архивы, глубоко вложенные данные и неизвестные форматы ключей могут остаться незамеченными. Стандартные upstream allowlists остаются частью правил. Ревью ресурсов и минимизация публикуемых файлов необходимы. Новые правила, более глубокие архивы и обновления версии следует вводить по конкретной потребности с повторением тестов. Защита не очищает уже опубликованный сайт или историю автоматически.

Исходный аудит и результаты внедрения: [отчёт](security-audit.md).
